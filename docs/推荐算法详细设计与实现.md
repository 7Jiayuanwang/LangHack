## 一、概述

### 1.1 背景

LangHack 早期推荐仅依赖管理员手动标记的"精选文章"（`is_featured` + `featured_priority`），所有用户看到的推荐内容完全相同，缺乏个性化能力。随着用户阅读行为数据的累积（阅读记录、收藏、学习记录、划线、习题作答），有充足的素材引入协同过滤。

### 1.2 目标

- **个性化**：不同用户看到不同推荐
- **相关性**：推荐与用户已读文章主题/难度相近的内容
- **多样性**：避免单一相似度过度聚焦
- **可靠性**：冷启动、数据稀疏、矩阵未生成等情况下有兜底
- **零停机**：每日重算不影响在线请求

### 1.3 数据规模

| 实体 | 当前规模 | 说明 |
|------|---------|------|
| 用户（STUDENT + USER） | ~180 | 参与协同过滤 |
| 文章（texts） | ~520 | 候选池 |
| 用户-文章交互对 | ~10,000 | UNION 去重后 |
| 文章相似度矩阵 | ~5,000 - 20,000 对 | 阈值 0.1 过滤后 |

小规模矩阵可直接在 MySQL 里用 SQL 完成，无需 Spark / Flink 等大数据组件。

### 1.4 推荐方式

**混合协同过滤**：Item-based CF 为主（60%） + User-based CF 辅助（40%） + 多级兜底。

- **Item-CF**：用户读过 A → 找与 A 相似的文章 B/C/D → 推荐（前提：A 和 B/C/D 有共同读者）
- **User-CF**：找与你行为相似的用户 U → 推荐 U 读过但你没读过的高分文章
- **兜底**：精选文章 → 难度匹配最新文章 → 忽略难度最新文章

### 2.2 离线计算链路

```
每日 03:00 Spring @Scheduled 触发
   │
   ├── 1. TRUNCATE _tmp 表
   ├── 2. INSERT ... WITH CTE（余弦相似度重算）→ _tmp
   ├── 3. RENAME TABLE 原子切换（_tmp ↔ 正式表）
   └── 4. DROP 旧表 + CREATE 新的空 _tmp
```

核心原则：**离线重算 + 在线查询分离**。相似度矩阵每日凌晨重算一次，在线请求只读取预计算好的矩阵，做简单 JOIN 与打分。

## 三、交互评分矩阵

### 3.1 设计思路

用户-文章的交互行为是多源、异构的（有二值的收藏，有连续的阅读时长）。需要一个统一的 **[0, 1] 区间评分** 作为协同过滤的输入向量。

### 3.2 评分公式

对每个 (user, text) 对，累加六个加权信号：

```
score(user, text) = min(1.0,
      0.2 × 是否已读
    + 0.2 × 是否完成
    + 0.3 × 是否收藏          ← 权重最高（显式偏好）
    + 0.1 × min(时长/600, 1)  ← 10 分钟封顶
    + 0.1 × 习题正确率
    + 0.1 × min(划线次数/10, 1)
)
```

### 3.3 权重设计理由

| 信号 | 权重 | 为什么 |
|------|------|--------|
| 收藏 | 0.3 | 收藏是显式、主动行为，信号最强 |
| 已读 / 完成 | 0.2 / 0.2 | 基本接触信号，高频但噪声大 |
| 阅读时长 | 0.1 | 连续值易受异常值干扰（忘关页面等），封顶防稀释 |
| 正确率 | 0.1 | 有条件生效（必须做题） |
| 划线 | 0.1 | 低频但深度信号，封顶防极端值 |

**封顶（clamp）设计**：时长封顶 600 秒（10 分钟）、划线封顶 10 次。如果封顶改成 3600（1 小时），一篇 5 分钟读完的短文 300/3600=0.083，乘权重 0.1 几乎归零，短文用户没得分。600 的选择使"认真读完短文的用户"能拿到满分 0.1。

### 3.4 视图定义（V13 优化版）

V12 原版视图用 `users CROSS JOIN texts` 产生 180×520=9.3 万行，再过滤 `score > 0` —— 大量零分行浪费 I/O。V13 改为**由交互源表 UNION 驱动**：

```sql
CREATE OR REPLACE VIEW v_user_text_interaction_scores AS
WITH user_text_pairs AS (
    SELECT user_id,    text_id FROM user_text_reads
    UNION
    SELECT student_id, text_id FROM text_learning_records
    UNION
    SELECT student_id, text_id FROM article_favorites
    UNION
    SELECT user_id,    text_id FROM underlines
)
SELECT
    utp.user_id,
    utp.text_id,
    -- 六个权重项...
    LEAST(<加权求和>, 1.0) AS interaction_score
FROM user_text_pairs utp
INNER JOIN users u ON u.id = utp.user_id AND u.role IN ('STUDENT', 'USER')
INNER JOIN texts t ON t.id = utp.text_id AND t.deleted = 0
LEFT JOIN user_text_reads utr ...
LEFT JOIN text_learning_records tlr ...
LEFT JOIN article_favorites af ...
LEFT JOIN (exercise_accuracy) sr ...
LEFT JOIN (underline_count) ul ...;
```

**关键点**：
- `UNION`（非 `UNION ALL`）去重，保证每对 (user, text) 只出现一次
- `INNER JOIN users ... WHERE role IN ('STUDENT', 'USER')` 排除管理员、教师的交互（他们的行为不代表学习者偏好）
- `INNER JOIN texts t ... t.deleted = 0` 自动过滤已删除文章

## 四、余弦相似度矩阵

### 4.1 公式

对两个文章 $t_1, t_2$，把所有共同读者的评分视为一个向量，余弦相似度：

$$
\text{sim}(t_1, t_2) = \frac{\sum_u s_1(u) \cdot s_2(u)}{\sqrt{\sum_u s_1(u)^2} \cdot \sqrt{\sum_u s_2(u)^2}}
$$

其中 $s_i(u)$ 是用户 $u$ 对文章 $t_i$ 的 interaction_score。分子求和只对"两篇文章都被评分的同一用户"，分母求和对"所有评过某文章的用户"。

用户相似度公式对称，只是行列角色对调（对文章向量求相似）。

### 4.2 关键实现修正（相对 v1.0）

设计文档 v1.0 的 SQL 有两个严重 bug：

**Bug 1：缺 `s1.user_id = s2.user_id` 约束**
```sql
-- ❌ 错：不同用户的评分交叉相乘，数学完全错误
JOIN v_scores s2 ON s1.text_id < s2.text_id

-- ✅ 对：只对同一用户做内积
JOIN v_scores s2 ON s1.user_id = s2.user_id AND s1.text_id < s2.text_id
```

**Bug 2：向量模长基底错**
模长应基于"所有读者对该文章的评分"计算，而不是"共同读者的评分"。改用 CTE 先独立计算 `item_norms`，再去除以。

### 4.3 最终重算 SQL（文章相似度）

```sql
INSERT INTO text_similarity_matrix_tmp (text_id, similar_text_id, similarity, created_at, updated_at)
WITH
  user_text_scores AS (
    SELECT DISTINCT v.user_id, v.text_id, v.interaction_score AS score
    FROM v_user_text_interaction_scores v
    INNER JOIN users u ON u.id = v.user_id AND u.role IN ('STUDENT', 'USER')
    WHERE v.interaction_score > 0
  ),
  vector_norms AS (
    -- 窗口函数：对每个 text_id 计算 √Σscore² 作为向量模长
    SELECT user_id, text_id, score,
      SQRT(SUM(POW(score, 2)) OVER (PARTITION BY text_id)) AS text_norm
    FROM user_text_scores
  ),
  pairs AS (
    -- 共同用户的内积分项（s1.score × s2.score），按 (t1, t2) 分组求和
    SELECT s1.text_id, s2.text_id AS similar_text_id, s1.score * s2.score AS dot_product
    FROM vector_norms s1
    INNER JOIN vector_norms s2
      ON s1.user_id = s2.user_id AND s1.text_id < s2.text_id
    WHERE s1.text_norm > 0 AND s2.text_norm > 0
  )
SELECT p.text_id, p.similar_text_id,
  ROUND(COALESCE(SUM(p.dot_product), 0) / NULLIF(SUM(s1.text_norm * s2.text_norm), 0), 4) AS similarity,
  NOW(), NOW()
FROM pairs p
INNER JOIN (SELECT DISTINCT text_id, text_norm FROM vector_norms) s1 ON s1.text_id = p.text_id
INNER JOIN (SELECT DISTINCT text_id, text_norm FROM vector_norms) s2 ON s2.text_id = p.similar_text_id
GROUP BY p.text_id, p.similar_text_id
HAVING similarity > 0.1;
```

**设计要点**：
- `s1.text_id < s2.text_id` 只存一半对，对称关系用查询时双向 OR 还原（见 §5.3）
- `HAVING similarity > 0.1` 过滤弱相似对，避免矩阵膨胀和推荐噪声
- `NULLIF` 保护零向量（全 0 评分的边界文章）

### 4.4 对称半矩阵存储

余弦相似度是对称的：$\text{sim}(A, B) = \text{sim}(B, A)$。存储时只存 `text_id < similar_text_id` 的一半（约 $N(N-1)/2$），查询时用 OR 还原：

```java
// 找所有和 seedId 相似的文章
WHERE (text_id = seedId OR similar_text_id = seedId) AND similarity > threshold
// 拿到行后：candidate = row.textId == seedId ? row.similarTextId : row.textId
```

**索引**：两侧列都需要索引（`idx_text_id` + `idx_similar_text_id`），V14 迁移补齐。

## 五、混合推荐算法

### 5.1 总体流程

```
recommend(userId, count):
    readTextIds ← user_text_reads.selectReadTextIds(userId)

    if readTextIds.size < 3:  ── 冷启动
        return fallback(featured + 最新难度匹配 + 最新)

    scoreMap ← {}
    accumulateItemCfScores(readTextIds, scoreMap)   ── Item-CF
    accumulateUserCfScores(userId,      scoreMap)   ── User-CF

    topIds ← scoreMap 按分降序取 Top count

    if topIds.size < count:
        return fallback(topIds + featured + 难度 + 最新)
    return materialize(topIds)
```

### 5.2 冷启动判定

- 阈值：`coldStartMinReads = 3`
- 判定依据：`user_text_reads` 记录数
- 为什么不用交互总量？避免查聚合视图的开销；读过 3 篇以上基本能产生可用的 Item-CF 信号

### 5.3 Item-CF 打分

```java
for each seedId in readTextIds:
    rows ← SELECT * FROM text_similarity_matrix
           WHERE (text_id = seedId OR similar_text_id = seedId)
             AND similarity > 0.2
           ORDER BY similarity DESC LIMIT 20

    for each row in rows:
        candidate ← row 中不是 seedId 的那一端
        if candidate not in excludeSet:
            scoreMap[candidate] += row.similarity × 0.6
```

- 单次 OR 查询同时取两侧（上一版是两次查询，已优化）
- 每个 seed 最多取 20 条最强相似（`per-seed-limit` 可配）
- 权重 `itemCfWeight = 0.6`

### 5.4 User-CF 打分

```java
// 步骤 1：找相似用户（双向 OR 一次查回）
rows ← SELECT * FROM user_similarity_matrix
       WHERE (user_id = userId OR similar_user_id = userId)
         AND similarity > 0.3

similarUserMap ← {}
for each row: similarUserMap[对端 userId] = max(similarUserMap[对端], row.similarity)

// 步骤 2：对每个相似用户，取其高分文章
for each (similarUserId, userSim) in similarUserMap:
    highScoreTexts ← SELECT * FROM v_user_text_interaction_scores
                     WHERE user_id = similarUserId
                       AND interaction_score > 0.5
                     ORDER BY interaction_score DESC LIMIT 10

    for each t in highScoreTexts:
        if t.textId not in excludeSet:
            scoreMap[t.textId] += userSim × t.interactionScore × 0.4
```

- `min-score = 0.5` 过滤"略微有兴趣"的弱信号
- 权重 `userCfWeight = 0.4`
- 同一 textId 被多个相似用户推到也会**累加**（越多相似用户喜欢，分越高）

### 5.5 加权合并

Item-CF 和 User-CF 的得分都进入同一个 `Map<Long, Double>`（`scoreMap.merge(candidate, score, Double::sum)`）。最终按值降序取 Top N。

**举例**：
- 文章 X 被用户两篇已读文章 A、B 相似命中（Item-CF），分别得分 0.3 和 0.2
- 文章 X 又被相似用户 U 高分读过（User-CF），得分 0.15
- 最终 X 得分 = 0.3 + 0.2 + 0.15 = **0.65**

### 5.6 兜底链

当 Top N 不足 `count` 个时，依次尝试：

**Step 5 — 精选兜底**：
```sql
WHERE deleted = 0 AND is_featured = 1 AND featured_priority > 0
  AND id NOT IN (excludeSet ∪ accumulatedIds)
ORDER BY featured_priority DESC, created_at DESC
LIMIT need
```

**Step 6a — 难度匹配兜底**：
- 难度 = 用户已读文章中出现最多的 `difficulty`（众数）
- 通过 `UserTextReadMapper.selectMostReadDifficulty` 一条 SQL 直接求众数（原实现会拉全部 Text 行包括 content 大字段到内存再分组，被优化掉了）

```sql
SELECT t.difficulty FROM texts t
INNER JOIN user_text_reads r ON r.text_id = t.id
WHERE r.user_id = ? AND t.difficulty IS NOT NULL
GROUP BY t.difficulty ORDER BY COUNT(*) DESC LIMIT 1
```

然后取该难度下最新的 `need` 篇未读文章。

**Step 6b — 忽略难度兜底**（最后一层保险）：
- 如果众数难度下也不够（小众难度 + 大量已读），直接按 `created_at DESC` 取最新未读文章。

这三层兜底保证推荐接口**永远**能返回 `count` 篇（除非整个文章库被用户读完，此时返回少于 `count` 是合理的）。

### 5.7 物化顺序

排序后的 `LinkedHashSet<Long>` 需要转成 `List<Text>`，但 `listByIds` 返回顺序是 DB 驱动的（ID 升序），会丢失打分排序。用 `Map<Long, Text>` 重映射保留顺序：

```java
Map<Long, Text> byId = textService.listByIds(ids).stream()
    .collect(Collectors.toMap(Text::getId, t -> t));
return ids.stream().map(byId::get).filter(Objects::nonNull).collect(Collectors.toList());
```

## 六、Shadow Table 零停机策略

### 6.1 为什么需要

直接 `DELETE + INSERT` 或 `INSERT ... ON DUPLICATE KEY UPDATE` 会持有行锁或表锁数秒至数十秒（矩阵量级 10k-100k 行），阻塞在线推荐查询。

### 6.2 策略

1. 提前建好同结构的 `text_similarity_matrix_tmp`
2. 重算时 `TRUNCATE _tmp`，然后 `INSERT ... SELECT` 到 _tmp（期间正式表继续读）
3. 用 MySQL `RENAME TABLE` 原子交换两张表：
   ```sql
   RENAME TABLE text_similarity_matrix     TO text_similarity_matrix_old,
                text_similarity_matrix_tmp TO text_similarity_matrix;
   ```
4. `DROP` 旧表 + `CREATE` 新的空 _tmp 备下次使用

### 6.3 耗时

- 步骤 2（INSERT）：几秒到几十秒，**不阻塞**读
- 步骤 3（RENAME）：**毫秒级**，唯一的"停顿窗口"
- 步骤 4（DROP + CREATE）：毫秒级

在线查询感受到的最长阻塞 < 50ms。

### 6.4 为什么不能 `@Transactional`

MySQL 的 DDL（TRUNCATE / RENAME / DROP / CREATE）会**隐式提交事务**。声明式事务对 DDL 无效，而且如果中间 INSERT 失败：
- `@Transactional` 试图回滚
- 但 TRUNCATE 已经提交了，无法还原
- 事务语义破坏，只会带来混淆

所以 `SimilarityMatrixScheduleTask` 的方法**不能标 `@Transactional`**。每一步失败会抛异常，已执行的 DDL 就留在那（这是 MySQL 的特性，非 bug）。

### 6.5 allowMultiQueries

`dropOldAndRecreateTmpText` 一条 @Update 里包含两个语句（`DROP` + `CREATE`），需要 JDBC 连接开启 `allowMultiQueries=true`。在 `application.yml` 的 JDBC URL 里已配置：

```
jdbc:mysql://localhost:3306/english_learning?...&allowMultiQueries=true
```

## 八、定时任务

### 8.1 Cron 表达式

```java
@Scheduled(cron = "0 0 3 * * ?")
public void scheduledRecompute() {
    recomputeAll();
}
```

每日凌晨 3:00 执行。选这个时间因为：
- 用户活跃低谷期（国内凌晨）
- 离线任务窗口充裕（不会和早 8 点的流量碰头）
- 当日行为产生的新数据可以全部纳入

### 8.2 手动触发接口

开发联调 / 紧急重算时可调用：

| 接口 | 方法 | 权限 | 说明 |
|------|------|------|------|
| `/api/admin/similarity/recompute/text` | POST | ADMIN/OPS | 只重算文章相似度 |
| `/api/admin/similarity/recompute/user` | POST | ADMIN/OPS | 只重算用户相似度 |
| `/api/admin/similarity/recompute/all` | POST | ADMIN/OPS | 两个都重算 |

**示例**：
```bash
curl -X POST http://localhost:8080/api/admin/similarity/recompute/all \
  -H "Authorization: Bearer <ADMIN_JWT>"
```

响应：
```json
{ "code": 200, "message": "全部相似度矩阵重算完成，耗时 3847ms", "data": null }
```

### 8.3 并发保护

Spring `@Scheduled` 默认单线程池执行，同一任务不会并发。但如果手动调接口的同时 cron 也触发，两个请求可能撞上同一个 TRUNCATE → 第二个会看到空表。生产环境建议：
- 避免在凌晨 3 点附近手动触发
- 或未来引入分布式锁（Redis）保护（当前单实例不需要）

## 十一、可调配置项

`application.yml`：

```yaml
recommendation:
  weight:
    item-cf: 0.6         # Item-CF 权重
    user-cf: 0.4         # User-CF 权重
  similarity:
    text-threshold: 0.2  # Item-CF 过滤阈值
    user-threshold: 0.3  # User-CF 过滤阈值
  cold-start:
    min-reads: 3         # 冷启动判定（< 3 条已读走兜底）
  user-cf:
    min-score: 0.5       # 相似用户文章的最低 interaction_score
    per-user-limit: 10   # 每个相似用户最多取 N 篇文章
  item-cf:
    per-seed-limit: 20   # 每个已读种子文章最多取 N 篇相似
```

### 调优建议

| 症状 | 可能原因 | 调整 |
|------|---------|------|
| 推荐太千篇一律（都是精选） | 用户交互不足 → 走兜底 | 降低 `cold-start.min-reads` / 确认矩阵是否重算过 |
| 推荐结果无关 | 阈值太低，弱相似也进榜 | 提高 `similarity.text-threshold` 到 0.3 |
| 推荐结果少 | 阈值太高 + 数据稀疏 | 降阈值到 0.1；或增大 `per-seed-limit` |
| User-CF 不生效 | 相似用户太少 | 检查 `user_similarity_matrix` 行数；降 `similarity.user-threshold` |

## 十三、性能评估

### 13.1 重算耗时（参考值，单实例 MySQL 8.0）

| 操作 | 当前规模耗时 |
|------|-------------|
| 文章相似度矩阵重算 | ~1-3 秒 |
| 用户相似度矩阵重算 | ~0.5-2 秒 |
| Shadow Table 切换（RENAME） | < 10 ms |
| DROP + CREATE tmp | < 50 ms |

### 13.2 在线查询耗时（p95）

| 场景 | 耗时 |
|------|------|
| 活跃用户（30 篇已读） | ~100-300 ms |
| 中度用户（10 篇已读） | ~50-150 ms |
| 冷启动用户（< 3 篇） | ~20-80 ms（只走兜底） |

### 13.3 性能优化决策

**已做**：
- V13 视图由 UNION 驱动替代 CROSS JOIN（行数 9.3w → ~1w）
- V14 补 `idx_similar_*_id` 索引（右侧查询从全表扫到索引扫）
- Item-CF 单次 OR 查询代替左右两次查询（DB 往返减半）
- `selectMostReadDifficulty` 直接 SQL 求众数（省下拉取全部 Text 行的开销）
- Shadow Table 替代 ON DUPLICATE KEY UPDATE（RENAME 毫秒级 vs 行锁秒级）

**未做但考虑过**：
- 所有 seed 合并为单个 `IN (...)` 查询：需要 window function + per-seed LIMIT，当前规模下 per-seed 查询够快
- Redis 缓存推荐结果：当前 p95 < 500ms 够用；未来用户增长后可引入

## 十四、已知限制与未来优化

### 14.1 限制

1. **实时性滞后**：当日新产生的阅读/收藏等行为，要到次日凌晨 3 点重算后才影响推荐。紧急用户可手动调接口。
2. **冷启动单调**：新用户前 3 次都看到同样的精选+最新推荐，缺乏探索。
3. **长尾文章曝光不足**：Item-CF 倾向把流量集中到热门文章（被读多 → 更多相似 → 更多推荐）。
4. **难度推断粗糙**：基于已读文章众数，没考虑"用户想挑战更难"的隐含意图。
5. **单机 MySQL 瓶颈**：用户增长到万级后，相似度重算可能需要分布式方案。

### 14.2 未来可做

| 阶段 | 内容 | 收益 |
|------|------|------|
| Phase 5 | Redis 缓存当日增量 → 实时反馈 | 降低滞后到分钟级 |
| Phase 6 | 多样性重排（MMR / DPP） | 避免推荐趋同 |
| Phase 7 | 引入内容特征（文章 tags, 主题）→ 冷启动解决 | 新文章/新用户也能推 |
| Phase 8 | 在线 A/B 实验平台 | 量化算法改动效果 |
| Phase 9 | 用户长期兴趣模型（衰减时间权重） | 近期行为权重更高 |

## 十五、故障排查

### 15.1 推荐接口返回空

**可能原因**：
1. 矩阵未计算 → `SELECT COUNT(*) FROM text_similarity_matrix;` 为 0
2. 用户未登录 → 接口直接返回空
3. 所有候选都被 exclude（用户读完了库）

**排查**：
```sql
-- 1. 看矩阵是否有数据
SELECT COUNT(*), MAX(updated_at) FROM text_similarity_matrix;
-- 2. 看用户已读数
SELECT COUNT(*) FROM user_text_reads WHERE user_id = ?;
-- 3. 看用户是否有交互评分
SELECT * FROM v_user_text_interaction_scores WHERE user_id = ? LIMIT 10;
```

### 15.2 推荐接口 401

**原因**：前端没带 JWT token

**排查**：
- 确认前端调用用的是 `@/api/texts` 而不是原生 `fetch`
- 浏览器 Network 面板看请求 Header 有没有 `Authorization: Bearer ...`
- 检查 token 是否过期（`/utils/request.js` 会处理 401 但可能静默失败）

### 15.3 定时任务不执行

**排查**：
- 启动日志有没有 "Scheduled task scheduled" 类似信息
- `AsyncConfig` 的 `@EnableScheduling` 注解是否存在
- 应用是否启动失败（参考 `logs/backend.log` 开头的 APPLICATION FAILED TO START）
- 服务器时区是否正确（cron 基于 JVM 本地时区）

### 15.4 Shadow Table RENAME 失败

**常见错误**：`Error Code: 1017. Can't find file: 'text_similarity_matrix_old.MYI'`

**原因**：上次重算中途失败，`_old` 表还在，RENAME 会冲突

**修复**：
```sql
DROP TABLE IF EXISTS text_similarity_matrix_old;
DROP TABLE IF EXISTS user_similarity_matrix_old;
-- 然后手动触发重算
```

### 15.5 slave-pool 警告

参考 `docs/TROUBLESHOOTING.md` 关于 `DynamicDataSource` 的说明。推荐系统不直接受影响（读走主库降级路径）。

| 术语 | 含义 |
|------|------|
